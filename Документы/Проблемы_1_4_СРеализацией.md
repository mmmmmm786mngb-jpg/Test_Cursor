# Technical Issues 1–4

🔧 Технические проблемы  

1. Запись замеров времени и логов в регистры сведений  
📍 Модули: `Catalogs/ВидыОперацийЗакрытияПериода/Ext/ManagerModule.bsl`  
⚙️ Проблемные операции: `Запись.Записать()`, `мз.Записать()`  
📝 Суть: По каждой операции происходит запись замеров времени выполнения. Однако существует множество операций, время выполнения которых меньше или сравнимо с самим временем логирования, что приводит к избыточным накладным расходам на запись в базу данных.  
💡 Предложение по решению: добавить константу `ПорогМинимальногоВремениЗамера`, в которой хранить минимальное время замеряемых операций (в миллисекундах). Операции, время выполнения которых меньше порога, не логировать.  
  
Реализация:  

- В процедуре `ВыполнитьИсполняемуюПроцедуруЗакрытияПериода` заведена переменная `МинимальноеВремяДляЛог` (пока фиксировано 500 мс), сравнивающая фактическую длительность исполняемой процедуры.`  
- Стартовое сообщение в журнале и запись результата теперь выполняются только при `МинимальноеВремяДляЛог = 0` либо если продолжительность ≥ порога, оставляя полное логирование для тяжёлых операций.  
- При длительности ниже порога и отсутствии отказа процедура выходит без вызова `ДобавитьЗамер`, что избавляет регистры от лишних записей.  
- Комментарии в коде фиксируют дальнейший шаг по переносу значения порога в параметры/константы, обеспечивая расширяемость решения.

2. Определение списка вычисляемых операций закрытия периода по каждой дате/портфелю/группе  
📍 Модули: `InformationRegisters/НастройкиЗакрытияПериода/Ext/ManagerModule.bsl`, `DataProcessors/ГрупповоеВыполнениеЗакрытияПериодов/Ext/ObjectModule.bsl`  
🔧 Функция: `ПланРеглОпераций()` (строка 324 оригинала)  
⚙️ Проблемная операция: `Запрос.Выполнить()`  
📝 Суть: запрос многократно строил план операций для каждого портфеля в каждом потоке, что порождало избыточные обращения к базе.  
💡 Предложение по решению: предварительно сформировать структуру таблиц значений и передавать её в параметры многопоточной процедуры, чтобы фоновые задания работали по готовому набору.  
  
Реализация:  

- В обработке `ГрупповоеВыполнениеЗакрытияПериодов` перед запуском потоков собирается соответствие `ПланРеглОперацийПоДням`: для каждого дня вычисляется единый набор операций по всем портфелям и складывается в `ДопПараметры`.  
- Процедура `СформироватьРеглОперацииПоГруппе` умеет извлекать нужную таблицу из соответствия и фильтровать её в памяти по портфелю и группе, возвращаясь к старому запросу только при отсутствии подготовленных данных.  
- Запрос в `ПланРеглОпераций` переработан: добавлены временные таблицы, индексы и раннее отсеивание, что снижает количество обращений к регистрам при единовременном расчёте.  
- Все изменения сохраняют обратную совместимость — при отсутствии параметров многопоточности используется прежний подход.

3. Определение в каждой операции статуса активности регламента  
📍 Модули: `DataProcessors/ГрупповоеВыполнениеЗакрытияПериодов/Ext/ObjectModule.bsl`, `CommonModules/ДлительныеОперации/Ext/Module.bsl`  
🔧 Функции: `ВыполнитьМногопоточноеЗакрытиеПериодовПортфелей`, `ПроверитьАктивностьРегламента`  
⚙️ Проблемная операция: `РегламентныеЗадания.НайтиПоУникальномуИдентификатору()`  
📝 Суть: проверка активности регламента выполнялась повторно для каждого потока, хотя статус не меняется внутри одной волны запуска.  
💡 Предложение по решению: позволить отключить проверку внутри потоков и выполнить её один раз в управляющем процессе.  
  
Реализация:  

- Перед запуском многопоточного закрытия в `ДопПараметры` устанавливается флаг `ПропуститьПроверкуАктивностиРегламента`.  
- Процедура `ПроверитьАктивностьРегламента` теперь читает этот флаг и, если он установлен, сразу возвращается без повторной загрузки фонового задания из регистра.  
- Благодаря этому запрос к `РегламентныеЗадания` и `ФоновыеЗадания` выполняется только на начальном этапе, а внутри потоков используется уже проверенное состояние.  
- Ускорение дополняется заменой «busy loop» паузы на `АванкорСервер.Пауза`, что снижает нагрузку на CPU во время ожидания повторов.

4. Очистка неактивных «исполнителей» (фоновых записей)  
📍 Модуль: `InformationRegisters/ИсполнителиЗакрытияПериодов/Ext/ManagerModule.bsl`  
🔧 Процедура: `ОчиститьНеактивныхИсполнителей()`  
⚙️ Проблема: прежний код оборачивал каждую попытку удаления в транзакцию и эксклюзивную блокировку, что вызывало задержки и конкуренцию.  
💡 Предложение по решению: отказаться от явных транзакций, оставить только проверку и удаление с отработкой ошибок.  
  
Реализация:  

- Новая версия собирает все GUID исполнителей списком без каких‑либо блокировок и транзакций.  
- Активные задания определяются отдельным проходом и помещаются в соответствие, чтобы не трогать действующие записи.  
- Для остальных записей выполняется попытка удаления без транзакций; ошибки, связанные с параллельным удалением, подавляются в блоке `Попытка…Исключение`.  
- За счёт снятия блокировок процедура стала неблокирующей для других потоков и перестала ждать завершения транзакций конкурентов.

📊 Визуализация процесса

📌 Архитектура системы:

Система состоит из трех уровней хранилищ:

  • GitLab Repository Центрального хранилища - главное хранилище всех репозиториев в банковской сети (Dev/QA/UAT и Релизный)
  • GitLab Repository сервера ВМ Яндекс - промежуточное хранилище для работы с виртуальной машиной
  • Локальные репозитории GIT - на рабочем компьютере (Dev/QA/UAT и Релизный) и в ВМ (только Dev/QA/UAT)

Автоматическая синхронизация между GitLab Repository сервера ВМ Яндекс и Центральным хранилищем (Dev/QA/UAT) происходит автоматически.

🔄 Описание бизнес-процесса

1

Инициация работы

Разработчик создает изменения на рабочем компьютере, используя локальные репозитории GIT (Dev/QA/UAT или Релизный)

2

Отправка в Центральное хранилище

Изменения отправляются через git push в GitLab Repository Центрального хранилища (Dev/QA/UAT или Релизный)

3

Инициация синхронизации

Центральное хранилище (Dev/QA/UAT) или GitLab Repository сервера ВМ Яндекс инициируют процесс автоматической синхронизации

4

Процесс синхронизации

Выполняется автоматическая синхронизация репозиториев между хранилищами

5

Локальные репозитории в ВМ

Виртуальная машина Яндекс получает изменения из GitLab Repository сервера ВМ через git clone/pull в локальные репозитории GIT (Dev/QA/UAT) для работы с Cursor AI

6

Разработка с Cursor

В ВМ выполняется разработка с использованием Cursor AI для генерации и оптимизации кода

7

Возврат в хранилище ВМ

Готовый код коммитится и отправляется в GitLab Repository сервера ВМ Яндекс через git push

8

Повторная синхронизация

После изменений в хранилище ВМ запускается процесс обратной синхронизации с Центральным хранилищем (Dev/QA/UAT)

9

Синхронизация на рабочую машину

Разработчик получает изменения на рабочую машину из Центрального хранилища через git pull в соответствующие локальные репозитории (Dev/QA/UAT или Релизный)

📦 Структура хранилищ и репозиториев

Архитектура хранилищ

  • GitLab Repository Центрального хранилища: Главное хранилище всех репозиториев в банковской сети (Dev/QA/UAT и Релизный)
  • GitLab Repository сервера ВМ Яндекс: Промежуточное хранилище для работы с ВМ (только Dev/QA/UAT)
  • На рабочем компьютере: Локальные репозитории GIT (Dev/QA/UAT и Релизный)
  • В ВМ Яндекс: Только локальные репозитории GIT (Dev/QA/UAT), релизный репозиторий отсутствует
  • Процесс синхронизации: Отдельный процесс автоматической синхронизации между GitLab Repository сервера ВМ Яндекс и Центральным хранилищем (Dev/QA/UAT)
  • Типы репозиториев: Dev (разработка), QA (тестирование), UAT (приемочное тестирование), Релизный (production)

📋 Преимущества множественных репозиториев:

  • Параллельная разработка: Одновременная работа над разными ветками (develop, main) без конфликтов
  • Изоляция окружений: Четкое разделение Dev/QA/UAT и Production репозиториев обеспечивает безопасность релизных версий
  • Гибкость переключения: Быстрое переключение между задачами через отдельные локальные репозитории
  • Централизованная синхронизация: Единая точка синхронизации через Центральное хранилище в банковской сети
  • Безопасность данных: Проверка службой информационной безопасности при каждой синхронизации
  • Резервное копирование: Автоматическое резервное копирование через Центральное хранилище в защищенной банковской сети
  • Полная история: Независимая история изменений для каждого типа репозитория (Dev/QA/UAT и Release)
  • Автоматизация: Синхронизация по наименованию репозиториев между хранилищами без ручного вмешательства
  • Удаленная разработка: Возможность работы в облачной ВМ с сохранением всех преимуществ локальной разработки

🌍 Мировые практики и аналоги

GitLab Flow с окружениями и автоматической синхронизацией

Наша схема соответствует GitLab Flow - стандартной практике разделения репозиториев по окружениям (Dev/QA/UAT/Production) с автоматической синхронизацией между ними. Это широко используется в enterprise-разработке:

  • GitLab Repository Mirroring: Встроенная функция GitLab для автоматической синхронизации репозиториев по наименованию между различными инстансами (центральное хранилище ↔ промежуточное хранилище)
  • Environment-based Promotion: Стандартная практика продвижения кода через окружения (Dev → QA → UAT → Production) с автоматической синхронизацией и проверкой безопасности на каждом этапе
  • GitLab Security Scanning: Автоматическое сканирование кода (SAST, DAST) при синхронизации репозиториев, встроенное в GitLab Ultimate и Premium

DevSecOps в финансовом секторе

Проверка безопасности при синхронизации репозиториев - обязательная практика в банковском секторе, соответствующая стандартам PCI DSS и требованиям регуляторов:

  • Shift-Left Security: Ранняя проверка безопасности на этапе синхронизации (практика крупных банков: JPMorgan Chase, Bank of America, Citibank)
  • Policy as Code: Автоматическая проверка соответствия политикам безопасности при каждой синхронизации через GitLab Security Policies
  • Compliance Automation: Автоматическая проверка соответствия стандартам (PCI DSS, SOC 2) при синхронизации через GitLab Compliance Management

Облачная разработка с синхронизацией

Использование облачных виртуальных машин для разработки с автоматической синхронизацией репозиториев - стандартная практика в крупных организациях:

  • GitHub Codespaces: Облачные окружения разработки с автоматической синхронизацией репозиториев и встроенной проверкой безопасности через GitHub Advanced Security
  • GitLab Remote Development: Работа в облачных ВМ с автоматической синхронизацией через GitLab Repository Mirroring и проверкой безопасности
  • Azure DevOps + Cloud Shell: Облачная разработка с синхронизацией репозиториев через Azure Repos и автоматической проверкой через Azure Security Center

Команды Git для работы с процессом

На рабочем компьютере (локальные репозитории GIT):

# Работа с репозиториями Dev/QA/UAT
cd achm_cursor_dev
git checkout develop
git add .
git commit -m "Описание изменений"
git push origin develop  # Отправка в Центральное хранилище (Dev/QA/UAT)
git pull origin develop  # Получение из Центрального хранилища

# Работа с релизным репозиторием
cd achm_cursor_release
git checkout main
git add .
git commit -m "Описание изменений"
git push origin main  # Отправка в Центральное хранилище (Релизный)
git pull origin main  # Получение из Центрального хранилища

В виртуальной машине Яндекс (локальные репозитории GIT - только Dev/QA/UAT):

# Создание локального репозитория Dev/QA/UAT из GitLab Repository сервера ВМ
git clone [GitLab_Repository_ВМ_Яндекс]/achm_cursor.git achm_cursor_dev
cd achm_cursor_dev
git checkout develop

# Работа с Cursor AI, внесение изменений
# ... разработка в репозитории Dev/QA/UAT ...

# Отправка изменений в GitLab Repository сервера ВМ
# (далее автоматическая синхронизация с Центральным хранилищем Dev/QA/UAT)
git add .
git commit -m "Изменения через Cursor AI"
git push origin develop

Автоматическая синхронизация по наименованию:

Синхронизация между GitLab Repository сервера ВМ Яндекс и GitLab Repository Центрального хранилища (Dev/QA/UAT) происходит автоматически в обоих направлениях по наименованию репозиториев. При каждой синхронизации служба информационной безопасности проверяет данные на соответствие политикам безопасности.

Управление множественными репозиториями

Для эффективной работы с множественными локальными репозиториями следуйте best practices:

  • Именование: Используйте понятные и согласованные имена для разработческих и релизных репозиториев (например, achm_cursor_dev, achm_cursor_release)
  • Синхронизация: Регулярно выполняйте git pull для получения актуальных изменений из Центрального хранилища
  • Ветки: Строго следите за тем, в какой ветке вы работаете (develop для разработки, main для релиза)
  • Коммиты: Делайте понятные коммиты с описанием изменений согласно Conventional Commits
  • Перед синхронизацией: Убедитесь, что все изменения закоммичены и отправлены в соответствующий репозиторий
  • Проверка безопасности: Помните, что все данные проходят проверку службой информационной безопасности при синхронизации
  • Изоляция окружений: Не смешивайте код из Dev/QA/UAT и Release репозиториев - используйте отдельные локальные копии

Безопасность и соответствие стандартам

Процесс разработан с учетом требований безопасности финансового сектора:

  • Автоматическая проверка: Каждая синхронизация проверяется службой информационной безопасности
  • Аудит: Все операции синхронизации логируются для аудита и соответствия требованиям
  • Изоляция: Разделение Dev/QA/UAT и Production репозиториев обеспечивает защиту критических данных
  • Централизованное хранилище: Все данные хранятся в защищенной банковской сети с соответствующими уровнями доступа
  • Резервное копирование: Автоматическое резервное копирование через Центральное хранилище

Цели и задачи Розничного Доверительного Управления

Бизнес-цели

  • Доступность инвестиций: Предоставление физическим лицам доступа к профессиональному управлению инвестициями с минимальными суммами вложений
  • Масштабируемость: Обработка большого количества мелких договоров ДУ (розничных клиентов) с высокой эффективностью
  • Автоматизация: Минимизация ручного труда за счет автоматической загрузки, обработки и исполнения сделок
  • Прозрачность: Обеспечение полной прозрачности операций и отчетности для клиентов
  • Соответствие регуляторным требованиям: Соблюдение всех требований ЦБ РФ и других регуляторов по доверительному управлению

Технические цели

  • Производительность: Обработка тысяч сделок в день с минимальным временем выполнения
  • Надежность: Гарантированное исполнение всех сделок в срок (T+n)
  • Масштабируемость системы: Возможность увеличения объемов без переработки архитектуры
  • Изоляция данных: Разделение обработки по пулам для независимой работы с разными сегментами клиентов
  • Мониторинг и контроль: Полная отслеживаемость всех операций и возможность быстрого реагирования на проблемы

Экономические цели

  • Снижение операционных затрат: Автоматизация процессов снижает потребность в ручном труде
  • Оптимизация комиссий: Автоматический расчет и распределение комиссий брокеров
  • Увеличение клиентской базы: Возможность обслуживания большего количества клиентов при тех же ресурсах
  • Конкурентное преимущество: Быстрое и точное исполнение сделок повышает конкурентоспособность

Ключевые особенности Розничного ДУ

  • Пул: РозницаДУ - специальный пул для розничных договоров доверительного управления
  • Загрузка: Используется команда "ФоновоеВыполнениеРозничноеДУ" с параметром ОтборПоПулу = 1
  • Исполнение: Фильтрация по пулу при распределении задач по потокам
  • Особенность: Код клиента извлекается из комментария сделки (для розничного ДУ)

Детали загрузки для Розничного ДУ

  • Команда: "ФоновоеВыполнениеРозничноеДУ" устанавливает ОтборПоПулу = 1
  • Особенность извлечения кода клиента: Для розничного ДУ код клиента берется из комментария сделки (удаляется последний символ)
  • Запрос по пулу: Используется функция ЗапросПоПулу(), которая связывает Пул.БрокерскийСчет с ТорговыеКоды.Ссылка
  • Фильтрация: Загружаются только сделки, связанные с торговыми кодами пула РозницаДУ
  • Создание объектов: В зависимости от типа сделки создается Документ.Сделка или БизнесПроцесс (СделкиTn/СделкиРЕПО)

Особенности исполнения для Розничного ДУ

  • Команда: "ФоновоеВыполнение_ПотоковоеИсполнениеСделокПул" - многопоточное исполнение с фильтрацией по пулу
  • Настройки: В параметрах обработки указывается список пулов (включая РозницаДУ)
  • Распределение: Задачи группируются по ДоговорДУ с фильтром по пулу, затем распределяются по потокам
  • Параллельное выполнение: Каждый поток обрабатывает свой список договоров Розничного ДУ
  • Фильтрация: В фоновом задании дополнительно фильтруются задачи по списку договоров пула

Ключевая особенность: Механизм исполнения сделки

Важно: Документ Сделка создается при создании задачи по точке маршрута ОткрытиеПлановойПозиции и сохраняется в реквизите Задача.Предмет. При закрытии плановой позиции происходит проверка существования документа (если его нет - создается новый).

Проведение документа Сделка (исполнение сделки) происходит при выполнении задачи по закрытию плановой позиции через механизм:

  1. ВыполнитьЗадачу() → вызывает ПриЗаписи (Задача.ВнебиржеваяСделка, ObjectModule.bsl)
  2. ПриЗаписи → если СинхронизоватьПредметПоЗадаче = Истина, вызывает СинхронизироватьСтатусПредметаЗадачи
  3. СинхронизироватьСтатусПредметаЗадачи → если Выполнена = Истина и Проведен = Ложь, выполняет ДокументОбъект.Записать(РежимЗаписиДокумента.Проведение)

Это и есть исполнение сделки - документ Сделка проводится, формируются движения по регистрам бухгалтерии.

Типы отчетов для Розничного ДУ

  • Отчеты по пулу:
    • СоставИСтруктураАктивовПула - показывает структуру активов пула
    • ДоходностьПоПулу - расчет доходности пула
    • ИзменениеДоходностиПоПулу - динамика изменения доходности
  • Отчеты по договорам:
    • ОбщийОтчетБрокера - сводный отчет по договорам брокера
    • СтатистикаИсполнений - детальная статистика исполнения сделок
    • СтатистикаИсполненийСКД - статистика через СКД
  • Все отчеты: Фильтруются по параметру Пул = РозницаДУ для получения данных только по розничным договорам

Анализ алгоритмов: Плюсы и минусы

Алгоритм загрузки сделок

Плюсы

  • Единый запрос для проверки существования сделок во всех типах объектов
  • Фильтрация по пулу позволяет изолировать обработку розничных клиентов
  • Гибкая система определения типа сделки (обычная, РЕПО, внебиржевая)
  • Обработка через Web Service обеспечивает интеграцию с внешними системами
  • Логирование всех операций для аудита

Минусы

  • Множественные обращения к справочникам внутри цикла (3000-5000 запросов на 1000 сделок)
  • Сложный запрос ОтобратьСделкиПоНомеру без фильтрации по дате (5-30 сек)
  • Последовательная обработка всех сделок без параллелизации
  • Извлечение кода клиента из комментария - хрупкая логика
  • Отсутствие кэширования справочников приводит к избыточным запросам

Алгоритм распределения по потокам

Плюсы

  • Жадный алгоритм обеспечивает равномерное распределение нагрузки
  • Группировка по ДоговорДУ минимизирует блокировки в БД
  • Сортировка по количеству задач (УБЫВ) оптимизирует распределение
  • Поддержка фильтрации по пулу для изоляции обработки
  • Масштабируемость - легко увеличить количество потоков

Минусы

  • Сортировка таблицы значений на каждой итерации (O(n log n))
  • Не учитывается реальное время выполнения задач разной сложности
  • Статическое распределение - нет динамической балансировки
  • Нет учета приоритетов договоров или клиентов
  • При большом количестве договоров запрос может быть медленным

Алгоритм исполнения сделок

Плюсы

  • Параллельное выполнение через фоновые задания ускоряет обработку
  • Изоляция по договорам ДУ минимизирует конфликты блокировок
  • Автоматическое выполнение задач снижает ручной труд
  • Поддержка разных типов сделок (Tn, РЕПО) в едином процессе
  • Возможность ожидания завершения всех заданий с проверкой статуса

Минусы

  • Запрос ПолучитьАвансы() выполняется при каждом проведении (70% времени)
  • Нет кэширования результатов запросов между задачами
  • Последовательное выполнение задач внутри одного договора
  • Отсутствие механизма повторных попыток при ошибках
  • Нет приоритизации срочных сделок

Алгоритм расчета комиссии

Плюсы

  • Группировка по АналитическийСчетДС позволяет корректно рассчитать комиссию
  • Пропорциональное распределение комиссии по сделкам справедливо
  • Корректировка последней сделки обеспечивает точность расчета
  • Поддержка разных алгоритмов расчета через РезультатАлгоритма

Минусы

  • Выполняется для всех сделок за день, даже если не требуется
  • Нет кэширования результатов расчета для одинаковых условий
  • Последовательная обработка по каждому АналитическийСчетДС
  • Нет механизма отката при ошибках расчета

Предложения по оптимизации

1. Кэширование справочников (Критично - ускорение 30-50%)

Проблема: При обработке 1000 сделок выполняется 3000-5000 запросов к справочникам внутри цикла.

Решение: Создать кэш справочников перед циклом обработки и использовать его внутри цикла.

Ожидаемый эффект: Сокращение запросов с 3000-5000 до 50-100 (только уникальные значения). Ускорение на 30-50%.

Места в коде: ПрочитатьНаСервере(), строки 2588, 2593, 2752 и др.

2. Оптимизация запроса проверки существования (Ускорение 20-40%)

Проблема: Запрос ОтобратьСделкиПоНомеру() выполняется 5-30 секунд без фильтрации по дате.

Решение: Добавить фильтр по дате сделки для ограничения выборки. Создать индексы на НомерВходящегоДокумента и Дата.

Ожидаемый эффект: Сокращение времени выполнения запроса в 2-5 раз.

Места в коде: ОтобратьСделкиПоНомеру(), строки 2139-2383.

3. Оптимизация запроса ПолучитьАвансы() (Критично - ускорение 50-70%)

Проблема: Запрос выполняется при каждом проведении документа Сделка, занимая 70% времени выполнения.

Решение: Кэшировать результаты запроса в рамках одной транзакции. Использовать временные таблицы для групповой обработки.

Ожидаемый эффект: Сокращение времени проведения документа в 3-5 раз.

Места в коде: Документ.Сделка.МодульОбъекта, строка 996.

4. Параллельная обработка загрузки сделок (Ускорение 3-5 раз)

Проблема: Последовательная обработка всех сделок в СоздатьОбъекты() занимает 30-60 минут для 5000 сделок.

Решение: Разделить список загрузки на группы по ДоговорДУ и обрабатывать каждую группу параллельно через фоновые задания.

Ожидаемый эффект: Ускорение обработки в 3-5 раз при использовании 4-8 потоков.

Места в коде: СоздатьОбъекты(), строка 1103.

5. Оптимизация алгоритма распределения по потокам (Ускорение 10-20%)

Проблема: Сортировка таблицы значений на каждой итерации цикла (O(n log n) для каждого договора).

Решение: Использовать приоритетную очередь (кучу) для быстрого поиска наименее загруженного потока. Сложность O(log n) вместо O(n log n).

Ожидаемый эффект: Ускорение распределения на 10-20% при большом количестве договоров.

Места в коде: РаспределитьЗадачиПоПотокам(), строка 672.

6. Батчинг запросов к регистрам (Ускорение 20-30%)

Проблема: Множественные запросы к регистрам бухгалтерии при проведении документов.

Решение: Группировать запросы в пакеты. Использовать временные таблицы для массовых операций.

Ожидаемый эффект: Сокращение количества обращений к БД и ускорение на 20-30%.

7. Индексация критических полей

Проблема: Отсутствие индексов на часто используемых полях в запросах.

Решение: Создать индексы на:

  • ДоговорДУ.Пул
  • ДоговорДУ.ТипКлиентаДУ
  • Задача.ВнебиржеваяСделка.СрокИсполнения
  • Документ.Сделка.Дата

Ожидаемый эффект: Ускорение запросов в 2-10 раз в зависимости от объема данных.

8. Асинхронная обработка отчетности

Проблема: Формирование отчетов блокирует пользовательский интерфейс.

Решение: Выполнять формирование отчетов в фоновых заданиях с уведомлением о готовности.

Ожидаемый эффект: Улучшение пользовательского опыта, возможность параллельной работы.

Варианты бизнес-реализации Розничного ДУ

1. Модель управляющей компании (УК)

Описание: Создание собственной управляющей компании с лицензией на доверительное управление.

Преимущества:

  • Полный контроль над инвестиционными решениями и процессами
  • Максимальная прибыль от комиссий и вознаграждений
  • Возможность создания собственных инвестиционных стратегий
  • Прямой контакт с клиентами

Недостатки:

  • Высокие требования к капиталу и лицензированию
  • Необходимость создания команды аналитиков и управляющих
  • Высокая ответственность и регуляторные требования
  • Длительный процесс получения лицензии

2. Партнерство с существующими УК

Описание: Сотрудничество с лицензированными управляющими компаниями для предоставления услуг ДУ клиентам.

Преимущества:

  • Быстрый выход на рынок без получения лицензии
  • Использование опыта и экспертизы партнера
  • Разделение рисков и ответственности
  • Фокус на привлечении клиентов, а не на управлении

Недостатки:

  • Зависимость от партнера
  • Разделение прибыли
  • Ограниченный контроль над инвестиционными решениями
  • Потенциальные конфликты интересов

3. Цифровая платформа (Robo-Advisor)

Описание: Автоматизированная платформа для управления инвестициями с использованием алгоритмов и ИИ.

Преимущества:

  • Низкие операционные затраты за счет автоматизации
  • Масштабируемость - обслуживание тысяч клиентов
  • Доступность 24/7 для клиентов
  • Персонализация стратегий на основе профиля риска
  • Прозрачность и автоматическая отчетность

Недостатки:

  • Высокие первоначальные инвестиции в разработку
  • Зависимость от технологий и их надежности
  • Ограниченная гибкость для сложных стратегий
  • Необходимость соответствия регуляторным требованиям

4. Гибридная модель (УК + Технологии)

Описание: Комбинация профессионального управления с автоматизированными процессами и цифровыми инструментами.

Преимущества:

  • Оптимальное сочетание экспертизы и автоматизации
  • Возможность обслуживания разных сегментов клиентов
  • Эффективность операционных процессов
  • Конкурентное преимущество через технологии

Недостатки:

  • Высокая сложность реализации
  • Необходимость балансировки между автоматизацией и контролем
  • Требования к квалификации персонала

5. Модель пулового управления

Описание: Объединение средств множества клиентов в пулы для коллективного управления (как в текущей реализации).

Преимущества:

  • Экономия на масштабе - снижение операционных затрат
  • Диверсификация портфеля за счет объединения средств
  • Профессиональное управление для мелких инвесторов
  • Прозрачность через единую отчетность по пулу
  • Автоматизация распределения результатов

Недостатки:

  • Ограниченная индивидуальность стратегий
  • Зависимость от размера пула
  • Сложность управления при росте количества клиентов
  • Необходимость балансировки интересов всех участников

Оптимизация Исполнений Сделок Розничного ДУ

Эпик: DU-OPT-2025 «Оптимизация исполнения сделок Т и Т–1 в Avancore DU»
Период выполнения: 27 ноября – 16 декабря 2025 (20 календарных дней, 15 рабочих дней)
Исполнитель: Senior 1C Developer
Задача Jira: IMAPPS-34094, IMAPPS-34560

1. Цели проекта

Основная цель

Оптимизация модуля Исполнения сделок Розничного ДУ для достижения целевых показателей производительности при обработке большого объема сделок.

Целевые показатели:

  • 100'000 сделок в торговый день за 3 часа (базовая конфигурация)
  • Снижение времени исполнения на 30-50% по сравнению с текущей версией
  • Обеспечение стабильной работы при увеличении нагрузки

Требования к сценарию тестирования:

  • Сделки по акциям (15 шт), облигациям (25 шт), О(-Б)ПИФам (10 шт)
  • Биржевые сделки на Мосбирже в режиме Т+ (Т0 заключение, Т+1 исполнение)
  • Пропорция Покупка/Продажа: 30/70
  • Количество торговых дней: 10 (по 100'000 сделок в день, всего 1 млн)
  • Количество клиентов: 1'000 (нормальное распределение)
  • Замеры на актуальной копии с продакшена

2. Выявленные проблемы

2.1. Проблемы производительности

Исходная ситуация: При обработке 100'000 сделок в торговый день время исполнения составляло 4-6 часов, что не соответствовало требованиям бизнеса.

Основные узкие места (выявлены через отладчик производительности 1С:Enterprise):

№ Модуль Функция Строка Критичность Проблема
1 Документ.Сделка ПолучитьАвансы() 996 ▲▲ КРИТИЧЕСКОЕ Сложный запрос к регистру бухгалтерии без явного приведения типов субконто, что приводило к ошибкам и замедлению
2 Документ.Сделка ТаблицыПоПродажам_БУ() 1647 ▲▲ КРИТИЧЕСКОЕ Пакетный запрос с неоптимальной структурой: использование ТИПЗНАЧЕНИЯ вместо оператора ССЫЛКА, отсутствие фильтрации по видам субконто
3 РегистрСведений.ЗначенияПараметровДоговораДУ ЗначенияПараметровДоговораДУ() 73 ▲ ВЫСОКОЕ Отсутствие кэширования параметров договора ДУ приводило к повторным запросам к базе данных для одинаковых договоров и дат

2.2. Проблемы параллельного выполнения

  • Жесткая блокировка количества потоков в обработке "внИсполнениеСделокТ+2_ДУ" (максимум 8 потоков)
  • Отсутствие возможности гибкой настройки количества потоков в зависимости от нагрузки и ресурсов сервера
  • Неоптимальное распределение нагрузки между потоками

3. Проведенные исследования

3.1. Подготовка инфраструктуры тестирования

Созданные инструменты:

  • Обработка-генератор «Перезапуск исполнений за период» — позволяет переиспользовать исторические данные для повторяемых замеров без генерации новых данных
  • Доработка регламентного задания «Исполнение сделок» — обеспечение возможности запуска исполнений за любой исторический период
  • Обработка генерации тестовых сделок — создание 100'000 сделок в день с заданными параметрами (50 активов, пропорция 30/70)
  • Отчет о статистике — анализ по активам, бизнес-процессам, видам операций для выбора объемов тестирования

3.2. Baseline-замеры производительности

Проведенные замеры:

  • Период 1: 01-02 сентября 2025 — 32'899 операций, 1'312 договоров
  • Период 2: 13, 14, 17 ноября 2025 — 28'670 операций, 4'476 договоров
  • Нагрузочное тестирование: 100'000 сделок в день — среднее время исполнения 5-6 часов

Собранные метрики:

  • Время выполнения запросов (топ долгих запросов)
  • Количество обращений к базе данных
  • Профилирование кода через отладчик производительности 1С:Enterprise
  • Анализ параллельности выполнения (создание потоков, администрирование выполнения)
  • Сравнение метрик работы в параллельном режиме

3.3. BA-анализ узких мест

Проведенный анализ:

  • Анализ параллельности: Изучение механизма создания потоков, администрирования выполнения и способов изменения режима распределения потоков
  • Детальный разбор топ-запросов: Анализ структуры запросов, выявление неоптимальных конструкций, поиск возможностей оптимизации
  • Фиксирование медленных мест: Выявление всех участков кода с низкой производительностью с анализом причин
  • Приоритизация: Составление приоритизированного списка оптимизаций по критичности влияния на производительность

4. Выводы и решения

4.1. Ключевые выводы

  • Основная проблема: Неоптимальные запросы к регистрам бухгалтерии без явной фильтрации по видам субконто и без кэширования часто используемых данных
  • Вторичная проблема: Ограничения на количество потоков параллельного выполнения не позволяют использовать ресурсы сервера оптимально
  • Направления оптимизации:
    1. Оптимизация запросов (явная фильтрация по видам субконто, улучшение структуры запросов)
    2. Кэширование параметров договора ДУ
    3. Индексация критических реквизитов
    4. Снятие ограничений на количество потоков

5. Реализованные доработки

5.1. Доработка 996: Получение остатков авансов

Проблема: В запросе использовалось прямое сравнение субконто с параметрами без явного приведения типов.

Решение: Добавлено явное приведение типов через функцию ВЫРАЗИТЬ для корректного сравнения субконто с параметрами запроса.

Результат: Устранены ошибки выполнения запроса, улучшена производительность за счет корректного использования индексов СУБД.

5.2. Доработка 1647: Формирование таблиц для проведения БУ

Проблема: Неоптимальная структура запроса: использование ТИПЗНАЧЕНИЯ, отсутствие фильтрации по видам субконто.

Решение:

  • Замена ТИПЗНАЧЕНИЯ на оператор ССЫЛКА с отрицанием
  • Добавлена функция ПолучитьВидыСубконтоПоСчету() для получения видов субконто
  • Добавлена явная фильтрация по видам субконто в запросах
  • Добавлена поддержка счета ЧПО через ОБЪЕДИНИТЬ ВСЕ
  • Изменена сигнатура функции для поддержки счета ЧПО

Результат: Значительное улучшение производительности пакетных запросов за счет оптимизации на уровне СУБД.

5.3. Доработка 73: Кэширование параметров договора ДУ

Проблема: При массовом проведении документов функция получения параметров вызывалась для каждого документа отдельно, даже если договор ДУ и дата одинаковые.

Решение:

  • Создана функция ЗначенияПараметровДоговораДУСКэшем() в модуле ОбщегоНазначенияДУПовтИсп с признаком ReturnValuesReuse = DuringSession
  • Добавлена сериализация параметров в XML для корректного кэширования
  • Нормализация даты до конца дня для улучшения эффективности кэширования
  • Применено в двух местах: Документ.Сделка и БизнесПроцесс.СделкиTn

Результат: При массовом проведении документов с одинаковым договором ДУ параметры получаются из кэша, а не из базы данных.

5.4. Доработка 1549: Подготовка таблицы остатков актива для валютного учета

Проблема: Отсутствие фильтрации по видам субконто хозрасчетных в запросе.

Решение: Добавлен параметр ВидыСубконтоХозрасчетные с явной фильтрацией по видам субконто (АналитическиеСчета и ЦенныеБумаги).

Результат: Более точная фильтрация данных на уровне базы данных, уменьшение объема обрабатываемых данных.

5.5. Доработка 2097: Получение суммы ОНВ для облигаций

Проблема: Два отдельных запроса к регистру бухгалтерии без явной фильтрации по видам субконто.

Решение:

  • Добавлен параметр ВидыСубконтоОблигации для явной фильтрации
  • Оптимизирована структура запроса с использованием подзапроса через ЛЕВОЕ СОЕДИНЕНИЕ

Результат: Улучшение производительности за счет явной фильтрации по видам субконто и оптимизации структуры запроса.

5.6. Доработка 167: Индексация ДоговорДУ в БП СделкиTn

Проблема: Отсутствие индексации реквизита ДоговорДУ в бизнес-процессе СделкиTn.

Решение: Добавлена индексация для реквизита ДоговорДУ в объекте метаданных БизнесПроцесс.СделкиTn.

Результат: Ускорение выполнения запросов, использующих фильтрацию по договору ДУ.

5.7. Доработка внутренней команды: Снятие ограничений на потоки

Проблема: Жесткая блокировка количества потоков (максимум 8) в обработке "внИсполнениеСделокТ+2_ДУ".

Решение: У реквизита КоличествоПотоков в полях "Минимальное значение" и "Максимальное значение" установлено 0 (снятие ограничений).

Результат: Возможность гибкой настройки количества потоков в зависимости от ресурсов сервера и нагрузки.

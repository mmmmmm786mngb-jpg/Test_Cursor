Регистр сведений «ТекущиеОбмены»

Назначение регистра

Регистр сведений ТекущиеОбмены используется для блокировки одновременного запуска обмена по одному узлу плана обмена «Источники обмена» в разных сеансах.

При старте обмена в регистр записывается запись «сеанс + узел обмена». Перед запуском обмена выполняется проверка: если для данного узла уже есть запись с активным сеансом, запуск запрещается с сообщением об ошибке. После завершения обмена (успешного или с ошибкой) запись удаляется вызовом УдалитьСеансОбмена.

Регистр реализует механизм блокировки «один обмен по узлу в один момент времени» в рамках подсистемы описания обменов (план «Источники обмена», модуль ОписаниеОбменовОбменСервер).

Сценарий: сервер 1С отключили во время обмена — запись осталась, обмены не проходят

Что происходит

Обмен по узлу плана обмена «Источники обмена» был запущен (вручную или по регламенту). До его завершения сервер 1С:Предприятие отключили (перезагрузка, аварийное выключение, остановка службы). Затем сервер включили снова.

В регистре ТекущиеОбмены остаётся запись с номером сеанса, в котором обмен запускался. Эта запись никогда не была удалена: процедура УдалитьСеансОбмена(Узел) вызывается только в конце ВыполнитьОбмен, а выполнение оборвалось из‑за отключения сервера.

При попытке снова запустить обмен по этому узлу пользователь получает ошибку: «Запуск обмена невозможен, т.к. обмен запущен в другом сеансе (…). Попробуйте позже.» — и создаётся впечатление, что обмены по узлу больше не проходят и запись «навсегда» блокирует запуск.

Почему запись «не удаляется сама»

В конфигурации нет фонового процесса, который бы периодически чистил регистр. Удаление записи возможно только в двух случаях:

  1. Нормальное завершение обмена — в конце ВыполнитьОбмен вызывается УдалитьСеансОбмена(Узел).
  2. Следующая попытка запуска обмена по этому узлу — при входе в ПроверитьВозможностьЗапускаОбмена(Узел) все записи по узлу сверяются со списком активных соединений (ПолучитьСоединенияИнформационнойБазы()). Записи, чей сеанс уже не в списке (в т.ч. после перезапуска сервера), считаются «осиротевшими» и удаляются из регистра в этой же процедуре. После этого, если активных сеансов обмена по узлу не осталось, новый обмен разрешается.

То есть «зависшая» запись удаляется не по расписанию и не при включении сервера, а при первом же запуске обмена по этому узлу после поднятия сервера.

Что делать: обмены снова начнут проходить

После включения сервера сеанс, в котором обмен когда‑то стартовал, уже не существует (все соединения после перезапуска новые). Поэтому при первой же попытке выполнить обмен по этому узлу (кнопка «Выполнить обмен» в форме узла, регламентное задание, обработка «Форма для работы с источником обмена»):

  1. Вызывается ПроверитьВозможностьЗапускаОбмена(Узел).
  2. В регистре находится старая запись по узлу; её номер сеанса отсутствует в ПолучитьСоединенияИнформационнойБазы().
  3. Запись удаляется как неактивная (осиротевшая).
  4. Исключение не вызывается, выполнение продолжается: ЗаписатьСеансОбмена(Узел), затем сам обмен, затем УдалитьСеансОбмена(Узел).

Рекомендация: после перезапуска сервера 1С достаточно один раз запустить обмен по проблемному узлу (вручную или дождаться регламентного задания). Первый запуск очистит старую запись и выполнит обмен; последующие будут работать как обычно.

Инструкция для того, кто перезапускает 1С (например, для обновления)

Чтобы после перезапуска обмены по узлам «Источники обмена» не блокировались из‑за старых записей в регистре ТекущиеОбмены, нужно добиться того, чтобы в системе пропали не только сеансы, но и соединения. Проверка обмена смотрит на ПолучитьСоединенияИнформационнойБазы() — если номер соединения из регистра всё ещё есть в этом списке, запись из регистра не удалится и будет ошибка «обмен запущен в другом сеансе».

Важно: если в консоли администрирования 1С завершить только сеанс, то соответствующее соединение может остаться в списке до тех пор, пока не будет новой попытки обращения к базе. Пока соединение числится активным, обмены по этому узлу будут блокироваться.

Что проверить и сделать при перезапуске:

  1. Выполнять полную остановку и запуск сервера 1С:Предприятие: остановить все компоненты кластера (рабочие процессы rphost и менеджер кластера rmngr), затем запустить службу снова. Так и сеансы, и соединения гарантированно сбрасываются — старые номера не останутся в списке соединений.
  2. Избегать «частичного» перезапуска (только один рабочий процесс, только перезапуск менеджера кластера без рабочих процессов и т.п.) — при нём данные о сеансах и соединениях могут сохраняться, старые номера продолжат возвращаться в ПолучитьСоединенияИнформационнойБазы(), записи в регистре не удалятся, обмены остановятся.
  3. После перезапуска при необходимости проверить в консоли администрирования 1С список соединений с информационной базой и убедиться, что нет «зависших» соединений (например, от регламентных заданий, которые выполнялись до перезапуска). При полной остановке и запуске кластера список будет пустым до первых новых подключений.

Регламентные задания обмена после перезапуска запустятся сами по расписанию; если перезапуск был полным, при первом же таком запуске процедура проверки удалит старую запись из регистра и обмен выполнится.

Если обмен после перезапуска по-прежнему не запускается

Ниже — отдельный разбор случая, когда ошибка «обмен запущен в другом сеансе» продолжает появляться после перезапуска сервера. Причина связана с тем, что такое номер соединения и при каких условиях он продолжает считаться «активным».

Что такое «номер соединения» в контексте регистра ТекущиеОбмены

В коде используются две вещи:

  • НомерСоединенияИнформационнойБазы() — возвращает номер соединения текущего сеанса. Это значение при записи в регистр попадает в измерение «Сеанс».
  • ПолучитьСоединенияИнформационнойБазы() — возвращает массив описаний активных соединений с информационной базой. У каждого элемента есть свойство НомерСоединения (и другие).

В архитектуре 1С:Предприятие (клиент-сервер) соединение и сеанс — разные сущности. Сеанс описывает активного пользователя ИБ и привязан к потоку обработки; соединение — канал доступа к кластеру (тонкий/толстый клиент, регламентное задание, веб-клиент, COM и т.д.). Сеанс при обращении к серверу «назначается» на соединение. Номер, с которым работает регистр ТекущиеОбмены, — это идентификатор, связывающий запись с конкретным соединением/сеансом в кластере.

Проверка «можно ли запускать обмен» делается так: по узлу читаются записи регистра (поле «Сеанс» = номер соединения). Затем для каждого номера из списка проверяется: есть ли он среди ПолучитьСоединенияИнформационнойБазы(). Если для записи такой номер в списке соединений есть — сеанс считается живым, запуск блокируется. Если нет — запись считается осиротевшей и удаляется из регистра.

Почему номер соединения может «оставаться» в списке после сбоя или перезапуска

По документации и практике платформы 1С возможны такие ситуации, когда старый номер соединения/сеанса продолжает учитываться и блокировка обмена не снимается:

  1. Сохранение данных сеансов при перезапуске менеджера кластера (rmngr). В руководстве администратора 1С указано: «Session data is retained when the service cluster restarts» — данные сеансов сохраняются при перезапуске сервисного кластера. То есть при перезапуске именно менеджера кластера (а не только рабочих процессов) информация о сеансах может остаться. Список соединений/сеансов, который возвращает ПолучитьСоединенияИнформационнойБазы(), формируется с учётом данных кластера; если старый сеанс там ещё числится, запись в регистре будет считаться активной и обмен не запустится.
  2. Аварийное завершение рабочего процесса (rphost) во время выполнения серверного вызова. В документации сказано: изменения данных сеанса не сохраняются в менеджере кластера, если рабочий процесс был аварийно завершён во время серверного вызова. То есть факт завершения сеанса мог не быть записан; сеанс может продолжать фигурировать в учёте кластера, и его номер — в списке соединений с точки зрения приложения.
  3. Задержка обнаружения обрыва соединения (2–3 минуты). При аварийном обрыве связи (сеть, выключение клиента) серверу 1С требуется порядка 2–3 минут, чтобы зафиксировать потерю соединения с клиентом. В этот период соединение может ещё считаться активным, и соответствующий номер — присутствовать в ПолучитьСоединенияИнформационнойБазы(). Если сразу после перезапуска сервера или обрыва связи снова запускают обмен, проверка может ещё «увидеть» старый номер.
  4. Неполный перезапуск в кластере. Перезапустили только часть компонентов (например, только рабочие процессы на одном сервере), а менеджер кластера или другие рабочие процессы — нет. Данные о сеансах хранятся в менеджере кластера; при таком перезапуске старые номера сеансов/соединений могут по-прежнему возвращаться в списке активных.
  5. Пул соединений (веб-клиент, регламентные задания). При завершении вызова соединение возвращается в пул, сеанс завершается. Если из-за сбоя или таймаута связка «сеанс–соединение» была учтена некорректно, номер соединения теоретически может ещё фигурировать в учёте до истечения таймаутов или до полной перезагрузки компонентов.

Итог: запись в регистре удаляется только когда в ПолучитьСоединенияИнформационнойБазы() больше нет соединения с таким номером. Всё, что сохраняет этот номер в списке активных (сохранение данных сеансов при перезапуске кластера, аварийное завершение rphost, задержка обнаружения обрыва, неполный перезапуск), будет приводить к тому, что обмен после перезапуска по-прежнему не запускается.

Что делать, если обмен так и не запускается

  1. Убедиться, что обмен запускается именно через подсистему «Описание обменов» (кнопка «Выполнить обмен» по узлу плана «Источники обмена», регламентное задание узла, обработка «Форма для работы с источником обмена»). Иначе регистр ТекущиеОбмены не используется и сообщение об ошибке может быть из другого механизма.
  2. Подождать 2–3 минуты после обрыва связи или перезапуска и снова попробовать запустить обмен — сервер может с опозданием пометить соединение как закрытое.
  3. Полный перезапуск сервера 1С:Предприятие: остановить все компоненты кластера (рабочие процессы и менеджер кластера), затем запустить снова. Так данные о старых сеансах не сохраняются, и при следующем запуске обмена «осиротевшая» запись будет удалена.
  4. Вручную удалить записи по узлу из регистра сведений ТекущиеОбмены (через конфигуратор, отчёт по регистру или код с привилегированным режимом). После этого запуск обмена по этому узлу снова станет возможен. Рекомендуется делать это при остановленных обменах и понимании, что «зависших» сеансов уже нет.
  5. В кластере: при необходимости перезапустить не только рабочие процессы, но и сервис менеджера кластера (полная перезагрузка службы 1С:Предприятие), чтобы сбросить учёт сеансов и соединений.

Алгоритм ПроверитьВозможностьЗапускаОбмена (удаление записей без соединений)

Ниже — схема того, как процедура определяет «осиротевшие» записи (по которым уже нет активного соединения) и удаляет их из регистра.

flowchart TD A([Начало]) --> B["Запрос по Узел: выгрузить записи регистра в таблицу ТекущиеОбмены"] B --> C{Таблица пуста?} C -->|Да| D([Выход, обмен разрешён]) C -->|Нет| E["Соединения = ПолучитьСоединенияИнформационнойБазы()"] E --> F["СеансТекущегоОбмена = 0"] F --> G["Цикл по каждому Соединение из Соединения"] G --> H["Найти в таблице строки, где Сеанс = Соединение.НомерСоединения"] H --> I{Найдены строки?} I -->|Да| J["Запомнить номер в СеансТекущегоОбмена"] J --> K["Удалить эти строки из таблицы (только из таблицы в памяти)"] K --> L{Ещё соединения?} I -->|Нет| L L -->|Да| G L -->|Нет| M["В таблице остались только строки, для которых НЕТ активного соединения"] M --> N["Цикл по каждой оставшейся СтрокаСеанса"] N --> O["МенеджерЗаписи: ключ Сеанс + УзелОбмена из строки"] O --> P["Прочитать запись из регистра"] P --> Q{Запись найдена?} Q -->|Да| R["Удалить запись из регистра"] R --> S{Ещё строки?} Q -->|Нет| S S -->|Да| N S -->|Нет| T{СеансТекущегоОбмена > 0?} T -->|Да| U["ВызватьИсключение: обмен запущен в другом сеансе"] T -->|Нет| D

Кратко: Записи регистра по узлу выгружаются в таблицу. По списку активных соединений из таблицы вычеркиваются строки, чей номер сеанса совпал с номером соединения — они считаются «живыми». В таблице остаются только записи, для которых соединения уже нет (например, после перезапуска сервера). По этим оставшимся строкам циклом читается и удаляется соответствующая запись в регистре сведений. Если был хотя бы один «живой» сеанс обмена, вызывается исключение; иначе обмен разрешается.

Вывод: когда запись из регистра не удалится и обмены прекратятся

Если в момент работы обмена произойдёт перезапуск 1С, запись в регистре всё равно не удалится и последующие запуски обмена будут падать с ошибкой «обмен запущен в другом сеансе» в одном и том же случае:

Номер соединения (который записан в регистре) после перезапуска продолжает возвращаться в списке активных соединений (ПолучитьСоединенияИнформационнойБазы()). Тогда алгоритм находит в таблице строку с этим номером, считает сеанс «живым», выставляет СеансТекущегоОбмена > 0, в цикле по «оставшимся» строкам эта запись не попадает (она уже вычеркнута), из регистра ничего не удаляется, и в конце вызывается исключение. Каждая новая попытка запуска обмена повторяет то же самое — обмены по узлу фактически прекращаются.

Такое возможно, в частности, когда:

  • перезапускали только менеджер кластера (сервис кластера), а данные сеансов при этом сохраняются — старый номер может ещё числиться в учёте;
  • рабочий процесс (rphost) был аварийно завершён во время серверного вызова — факт завершения сеанса мог не сохраниться в менеджере кластера;
  • сразу после перезапуска или обрыва связи прошло меньше 2–3 минут — сервер с задержкой помечает соединение как закрытое;
  • выполнен неполный перезапуск (только часть рабочих процессов или только один узел кластера) — старые номера сеансов/соединений могут по-прежнему возвращаться.

В этих ситуациях для разблокировки нужно либо дождаться исчезновения старого номера из списка соединений (время, полный перезапуск), либо завершить соответствующий сеанс в консоли администрирования 1С, либо вручную удалить записи по узлу из регистра сведений ТекущиеОбмены.

Итог

Регистр сведений ТекущиеОбмены блокирует одновременный запуск обмена по одному узлу плана «Источники обмена» в подсистеме описания обменов. Если обмен не завершился из‑за отключения сервера 1С, запись в регистре остаётся и не удаляется фоновыми процессами; при первой же следующей попытке запуска обмена по этому узлу процедура ПроверитьВозможностьЗапускаОбмена удалит её как осиротевшую и обмен выполнится. Достаточно один раз снова запустить обмен (вручную или по регламенту).

Обмены через ОбменДаннымиСервер (сценарии, файл, веб-сервис) этот регистр не используют.
